# CodexDoc

Локальное Windows-приложение для подготовки документов с внешним ИИ-агентом. CodexDoc собирает материалы, правила доступа и настройки оформления в рабочую папку. Агент заполняет содержание; движок создаёт редактируемый DOCX, обновляет поля и оглавление, экспортирует PDF и проверяет результат.

**[Подробное иллюстрированное руководство пользователя: откройте «Как работать.html» в браузере](<./Как работать.html>).** Гид автономный, работает без интернета; в приложении доступен через кнопку **«Как работать ?»**.

Приложение не запускает ИИ, не сочиняет пользовательское задание и не передаёт материалы в облако. Пользователь самостоятельно запускает агента и решает, какие файлы ему предоставить. Рабочий цикл: **контекст и правила → внешний агент → сборка и проверка**.

## Установка и запуск

Требуются Windows x64, интернет для первоначальной установки и около 2 ГБ свободного места. После установки основной цикл приложения работает офлайн. Доступ к сети у внешнего агента регулируется отдельно его средой и выбранным профилем.

1. Запустите [Настроить.cmd](./Настроить.cmd). Скрипт [setup.ps1](./scripts/setup.ps1) устанавливает Python и зависимости через `uv`, затем отдельный локальный LibreOffice.
2. Откройте [CodexDoc.cmd](./CodexDoc.cmd). Лаунчер проверяет окружение и запускает Qt-интерфейс; при отсутствии компонентов предлагает настройку.

Версии Python **3.13.9** и LibreOffice **25.2.7.2**, URL и SHA-256 установщика рендерера закреплены в [runtime.lock.json](./runtime.lock.json); Python-зависимости закреплены в [uv.lock](./uv.lock). Проект поддерживает Python `>=3.13,<3.14`. Системные Word и LibreOffice не требуются.

| Расположение в репозитории | Назначение |
| --- | --- |
| `.venv/` | Окружение приложения |
| `.runtime/` | Управляемые Python и рендерер |
| `data/` | Настройки, черновики, библиотека, кеш анализа, журнал |
| `workspaces/` | Рабочие папки по умолчанию; расположение можно выбрать в UI |

Встроенные шаблоны используют установленный в Windows Times New Roman. `doctor` проверяет его наличие; файлы шрифта входят в отпечаток сборки. При отсутствии выберите доступную гарнитуру или установите лицензированный шрифт. Шрифты Windows вместе с проектом не распространяются.

## Архитектура рабочей папки

| Файл / папка | Назначение и контракт |
| --- | --- |
| `INSTRUCTIONS.md` | Читаемая инструкция: профиль, задача, материалы и ограничения, порядок работы, справка по движку |
| `AGENTS.md` | Совместимая инструкция для агентов; в новой папке содержит тот же сгенерированный текст |
| `AGENTS.codexdoc-*.md` | Актуальные инструкции рядом с сохранёнными пользовательскими или старыми файлами |
| `task.md` | Название и текст пользовательского задания; снимок `workspace.json → requirements` |
| `workspace.json` | Версия движка, режим, постановка, источники, роли, SHA-256, исключения |
| `template.json` | Снимок оформления, provenance, нерешённые вопросы и статус шаблона |
| `profile.json` | Снимок автономности, глубины проверок, политики интернета и ошибок |
| `document.json` | Метаданные и типизированные блоки содержания; основной источник последующих сборок |
| `analysis/baseline.json` | Цель, границы, ключевые положения и их основания |
| `analysis/` | Извлечения, пакеты содержательной проверки, заключения и их история |
| `schemas/` | JSON Schema документа, шаблона, workspace, baseline, заключений и примеры блоков |
| `sources/` | Материалы с ролью `citable`: изучение и цитирование |
| `context/` | `context_only`: внутреннее изучение без упоминаний, ссылок и библиографии |
| `template/` | `requirements_style`: методические требования и оформление без цитирования |
| `norms/`, `assets/` | Локальные нормативные основания и ресурсы документа |
| `doc.cmd`, `engine.json` | Привязка к интерпретатору и движку; запуск CLI из любой текущей директории |
| `.cache/` | Отпечатки, промежуточная сборка и подтверждения просмотра |
| `output/` | `document.docx`, `document.pdf`, `checks.json`, `checks.txt`, `pages/`, `overview*.png` |

Роль хранится единственным полем `role`: `citable`, `context_only`, `requirements_style`. Старое поле `policy` мигрирует при чтении. Исключённые файлы находятся в `excluded_sources`, не копируются в подготовленную папку и не используются агентом.

Повторная подготовка обновляет входные настройки, сохраняя блоки содержания агента. Ручные изменения инструкций не затираются: актуальный текст может быть записан в отдельный версионный файл. Если `task.md` изменён вручную, обновление останавливается до согласования текста с полем задания. Приложение хранит черновик отдельно; **«Папка не обновлена»** означает расхождение черновика и подготовленных файлов.

Стабильный ID блока позволяет адресно изменять содержание. Пример абзаца:

```json
{"id": "results-description", "type": "paragraph", "text": "Описание результата.", "citations": ["s001"]}
```

Библиография формируется по `citations` абзацев. Перед цитированием источник должен иметь проверенную запись `reference` и `reference_verified=true`. Ручной дубль списка литературы и технические маркеры `[s007]` в тексте не нужны. Контекст и образцы не включаются в библиографию и `provenance`.

## CLI и автоматизация

В подготовленной рабочей папке PowerShell запускает команды через связанный с ней лаунчер:

```powershell
& .\doc.cmd inspect
& .\doc.cmd build
& .\doc.cmd check
```

| Команда `doc.cmd` | Назначение |
| --- | --- |
| `inspect` | Инвентаризация источников, норм, ресурсов, provenance, SHA-256; актуальность проверок |
| `build` | DOCX → обновление полей и оглавления → PDF → проверки |
| `build --force` | Принудительная пересборка |
| `build --preview` | Просмотр чернового шаблона с `draft`/`unresolved`; результат не итоговый |
| `check` | Повторная проверка текущих артефактов и их актуальности |
| `source-preview --id s001 --page 1 --page 2` | PNG разрешённых страниц PDF-источника в `analysis/previews/` |
| `review --page 2 --note "Проверены таблица и подпись"` | Фиксация фактического визуального просмотра страницы |
| `patch --id block-id --text "Новый текст"` | Адресное изменение текстового блока; затем нужен `build` |
| `refresh-instructions` | Новые инструкции текущего движка рядом с исходными, обновление схем |
| `publish-template` | Публикация проверенного шаблона в локальную библиотеку |
| `extension --name word-count` | Запуск зарегистрированного расширения; `--request` принимает JSON запроса |
| `doctor` | Диагностика окружения и шрифта |

Глобальный CLI запускается из корня репозитория. Путь рабочей папки идёт **после команды**, а у `content-review` перед действием:

```powershell
& .\.venv\Scripts\python.exe -m codexdoc gui
& .\.venv\Scripts\python.exe -m codexdoc templates
& .\.venv\Scripts\python.exe -m codexdoc create --name "Отчёт" --template lab
& .\.venv\Scripts\python.exe -m codexdoc inspect "D:\Работы\Отчёт"
& .\.venv\Scripts\python.exe -m codexdoc build "D:\Работы\Отчёт"
& .\.venv\Scripts\python.exe -m codexdoc content-review "D:\Работы\Отчёт" status
```

`create --source` добавляет материалы; `--template-analysis` выбирает технический режим анализа шаблона. `create --example` создаёт демонстрацию конвейера, а не выполненную работу. `inspect` также принимает путь отдельного файла; `--output` сохраняет анализ в JSON. Режим workspace не подменяет прямо поставленную пользователем цель.

### Содержательная проверка

В новых папках она обязательна для `ready`. Агент заполняет `analysis/baseline.json`: `goal`, `scope`, `items`; у каждого положения есть `id`, `text`, `kind` и `basis` с точным `locator`, для источника также `source_id`. Допущения и предложения не становятся утверждёнными требованиями автоматически.

Для каждого этапа `plan`, `requirements`, `final`:

1. Подготовьте пакет командой `prepare --stage <этап>`.
2. Прочитайте `analysis/review-packet-<этап>.json` и разрешённые оригиналы. Агент заполняет `response_example` в отдельный файл заключения.
3. Передайте заключение через `submit --input ...`. Только затем переходите к следующему этапу.

```powershell
& .\doc.cmd content-review prepare --stage plan
# Агент сохраняет заполненное заключение в analysis/assessment-plan.json.
& .\doc.cmd content-review submit --input analysis/assessment-plan.json
# Повторить prepare/submit для requirements и final с отдельными заключениями.
& .\doc.cmd content-review status
& .\doc.cmd build
```

Каждому критерию нужен обоснованный вывод. `coverage` связывает `item_id` с `block_ids`; `missing`, `changed`, `unresolved` сохраняют проверку незавершённой. `findings` указывает фрагмент, причину и исправление. Изменение содержания, постановки, материалов или настроек аннулирует заключения всех трёх этапов. История хранится в `analysis/review-history/`.

В старой папке процесс включается командой `content-review init`, затем выполняется `refresh-instructions`. Движок проверяет структуру и актуальность заключений, а не истинность оценки агента. Внутренние пакеты могут содержать конфиденциальный контекст.

### Статусы и коды возврата

| Статус | Значение |
| --- | --- |
| `blocked` | Известная ошибка, отсутствующая или устаревшая сборка |
| `review` | Документ собран; требуется содержательное заключение и/или визуальный просмотр |
| `preview` | Предпросмотр черновика; нельзя подтвердить как итоговый или опубликовать |
| `ready` | Выполнены проверки выбранного профиля, содержательная проверка при её обязательности и требуемый просмотр |

Коды CLI: **`0`** — успешная команда, включая предпросмотр; **`2`** — блокирующая ошибка; **`3`** — документ собран, требуется просмотр/проверка. Для автоматизации читайте также `status` и `findings` в отчёте, а не только код завершения.

Отпечаток сборки учитывает содержание, настройки, код движка, окружение и шрифты. Целостность источников и итоговых файлов проверяется отдельно. Сохранённый `ready` без проверки актуальности не гарантирует готовность. Ручные изменения `output/document.docx` будут заменены следующей сборкой из `document.json`.

## Расширения и разработка

Встроенное расширение `word-count` возвращает метрики слов и символов. Доверенные Python-провайдеры подключаются через entry points группы `codexdoc.extensions`. Процессные адаптеры регистрируются массивом в `data/extensions.json`:

```json
[
  {
    "name": "external-count",
    "version": "1",
    "kind": "process",
    "command": ["D:/CodexDoc/.venv/Scripts/python.exe", "D:/CodexDoc/examples/word_count_adapter.py"],
    "timeout_seconds": 60
  }
]
```

Пути в примере замените фактическими. [Пример адаптера](./examples/word_count_adapter.py) читает один JSON из stdin и возвращает один JSON в stdout: `artifacts`, `findings`, `metrics`. Артефакты допускаются только внутри `assets/` или `output/`. Реализованы тайм-аут, проверка контракта и путей, контроль целостности и кеширование. Python-адаптеры получают принудительный UTF-8.

Отдельный процесс изолирует зависимости, но не является защитной песочницей. Расширения регистрируются явно; материалы задания никогда не исполняются как плагины. Результат расширения не заменяет основной отчёт проверок.

### Окружение и проверки

```powershell
uv sync --locked --extra dev
& .\.venv\Scripts\python.exe -m pytest
& .\.venv\Scripts\ruff.exe check codexdoc scripts tests examples
& .\.venv\Scripts\ruff.exe format --check codexdoc scripts tests examples
& .\.venv\Scripts\pyright.exe
& .\.venv\Scripts\python.exe -m build --no-isolation
```

Интеграционные проверки используют управляемый LibreOffice. Тестовые подтверждения просмотра проверяют машину состояний, но не заменяют визуальную оценку документа. Исходный архив включает HTML-гид; для запуска настольного приложения нужен полный checkout/архив с лаунчерами, скриптами и локальным runtime.

### Технические границы

- Это среда сборки структурированных документов, а не универсальный редактор произвольного DOCX. Поддержаны заголовки, абзацы, прямоугольные таблицы, изображения, списки, простые редактируемые OMML-формулы, приложения и библиография.
- Титул задаётся блоками на ширину области текста, город/год закрепляются снизу. Произвольные рамки, боковые колонки, разные правила секций, объединённые ячейки и сложная математическая вёрстка требуют расширения.
- Настройки `title_layout`, `contents_format`, `bibliography_format`, `structural_heading_style`, `structural_numbered` применяются штатной сборкой. Списки людей находятся в `metadata.authors` и `metadata.reviewers`.
- Анализ DOCX измеряет секции и стили; PDF не доказывает исходные поля и стили DOCX. Скан без текстового слоя не распознаётся автоматически. Реквизиты из явно подписанных полей извлекаются локально; неоднозначные значения проверяет внешний агент.
- Контроль контекста обнаруживает запрещённые ссылки и явные имена файлов. Смысловой пересказ, достоверность содержания и полное соответствие каждому пункту ГОСТ проверяет человек/агент по первоисточникам.
- Экспорт выполняется фиксированным LibreOffice; Word может отображать отдельные элементы иначе. При переносе приложения обновите привязку `doc.cmd` либо используйте сборку через UI.
- Лицензии PySide6/Qt, PyMuPDF, LibreOffice и остальных зависимостей действуют отдельно; их тексты сохраняются в установках компонентов.

## История версий

### 0.4.0

- Настраиваемые титул, оглавление, библиография, структурные заголовки, соавторы и проверяющие.
- Desktop Studio: проекты и автосохранение, три семантические корзины, живые инструкции, ручная передача агенту, сборка и контроль актуальности.
- Rosé Pine Main/Dawn, режимы «Авто / Светлая / Тёмная», автономный пользовательский гид.

### 0.3.0

- `analysis/baseline.json`, этапы `content-review` для плана, требований и итогового текста.
- Блок `requirement`, контроль технических ссылок и ручного дубля библиографии, редакторские предупреждения и обзор страниц.
- `ready` в новых папках требует актуальных содержательных заключений и просмотра.

### 0.2.0

- Инвентаризация источников и нормативов, provenance и SHA-256; безопасное обновление инструкций.
- Повторная проверка старых шаблонов, отдельный `preview`, локальный `source-preview`.
- Изоляция контекста, адресные правки, контроль целостности и UTF-8 для Python-адаптеров.
